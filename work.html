How a build
gets chosen.

Four filters that decide whether an idea becomes a project.

01It has a real userThe first user is usually me, on a device I actually carry. That keeps the requirements honest.
02It has a hard edgeA constraint that cannot be designed away: a phone, a protocol, a moving batter, a bad connection.
03It can be shownA working path is more useful than a roadmap. The build has to survive a short demonstration.
04It can be left aloneThe system should still make sense after a month away from it. That is the maintenance test.

The build
loop.

The sequence that turns an idea into something I can show.

  1. 01ObserveNotice a repeated friction or a question that will not leave.
  2. 02SketchDraw the smallest useful path. Decide what the system will not do.
  3. 03BuildMake the path work on the target device before adding breadth.
  4. 04BreakTest the old phone, the bad connection, the missing permission.
  5. 05ExplainWrite the readme or the interface copy. If it cannot be explained, it is not ready.
  6. 06LeaveClose the loop with notes and the next open question.

What ships
first.

The first release is a path, not a feature list.

01 / AgentOne useful loop

A single task that can be completed end to end, with visible state and a recovery path.

02 / DeviceOne target

The phone in my pocket before the generic desktop case. The constraints make the design honest.

03 / VisionOne movement

A useful read of a batting stance before a full biomechanics platform.

04 / WebOne page

A route that loads fast, works offline and can be read without a tutorial.

05 / NetworkOne room

A peer-to-peer session that connects without an account or a server.

06 / ToolOne repair

A tool that fixes the specific failure it was built for, then gets out of the way.

Constraints that
improve the work.

The limits I try to keep in the brief.

  • No account unless the product genuinely needs identity.
  • No backend unless the work cannot be done locally.
  • No dashboard unless someone will make a decision from it.
  • No animation unless it explains a state change.
  • No dependency unless it removes more code than it adds.
  • No release until it has been used on the target device.

Interfaces with
a high craft bar.

The visible part is not decoration.

An interface is where the system explains itself. I care about hierarchy, type, timing and the small states that tell a person whether their action landed. A beautiful screen with a hidden error path is still a broken screen.

The work here ranges from agent consoles to payment studies. The common rule is that the interface should make the system more legible, not more mysterious. If the design needs a paragraph of explanation before it makes sense, the design is not finished.

Definition
of done.

The checks I use before an archive entry is called complete.

  • The primary path works on the target device.
  • The error path is visible and recoverable.
  • The readme explains how to run it from a clean checkout.
  • The build does not depend on a secret local setup.
  • The interface has a keyboard and touch path.
  • The next open question is written down.

Signals I
care about.

Not vanity metrics. Evidence that the system is real.

01Works offlineThe useful path does not vanish when the connection does.
02One commandA clean checkout can be running without a setup ritual.
03Readable stateA person can tell what the system is doing without opening a log.
04Survives absenceThe project still makes sense after a month away from it.

Open source
posture.

What is public, what is private, and why.

The lab projects are public because the code is more useful than a description. The core systems remain private while they are still changing under a real user. Release 01 is the point where that boundary gets a proper public shape.

The archive is not a museum. It is a set of past answers to questions that are still live. If an old project becomes relevant again, it can be rebuilt instead of preserved exactly as it was.
