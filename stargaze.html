The
name.

Why the branch is called Stargaze.

Stargaze is the part of the work that looks past the current release. It is a software house, not a personal brand: a place to hold the agents, tools and vision systems under one standard.

The name is a direction, not a promise. The useful version is built close to the metal, released when it holds, and allowed to stay small enough to understand.

Local first,
concretely.

What the principle means in the build.

  • The primary task works with the network switched off.
  • The app tells you when a cloud model is being used.
  • Files stay readable on the device that created them.
  • A failed sync does not erase the local copy.
  • The user can export the useful data without a support ticket.
  • A local model can be swapped without rebuilding the interface.

Model
routing.

The choice between local and hosted is part of the product.

A router should not be a magic switch. It should know the task, the device, the latency budget and the privacy cost. If a request needs a hosted model, the interface should say so before the data leaves.

The first version is deliberately simple: a small policy table, a visible decision and a manual override. The interesting work is not the model list. It is making the trade-off understandable when the user is in a hurry.

Control

Tools and
permissions.

The rules that keep an agent useful without making it reckless.

  • Every tool has a name, a scope and a visible result.
  • Destructive actions require a confirmation that names the target.
  • The agent can explain why it chose a tool, not only which one.
  • A failed call leaves the workspace in a recoverable state.
  • The permission model is the same on phone and desktop.
  • The user can stop the loop without killing the app.

Voice as an
interface.

Speech is a channel, not a personality.

The voice layer is useful when the hands are busy or the screen is far away. It is not a reason to make every interaction a performance. The system should support a short command, a longer dictation and a silent fallback.

The hard parts are interruption, confirmation and the moment a spoken request turns into a tool call. Those are interface problems before they are model problems.

Vision as a
sensor.

A camera is only useful if it produces a decision.

Cricket Motion started with a simple question: can a phone camera tell a batter something useful about the swing? The answer has to be more specific than a skeleton on a screen. It has to connect a measurement to a change in the next repetition.

The first release is a session tool, not a coaching oracle. It should capture cleanly, show the useful angle and keep the data honest about what it can and cannot see.

Android as a
first-class target.

The phone is a computer, not a preview.

Most of the work assumes a rooted Android device can be a real workstation. That means Termux, local files, background services and a permission model that is treated as part of the product.

The constraint is useful. A tool that survives a phone has fewer hidden assumptions than one that only runs on a desk with a reliable power supply.

Security
posture.

The baseline for a system with device access.

  • Secrets stay out of the repository and out of the interface.
  • The agent cannot silently widen its own permissions.
  • Tool output is treated as untrusted input.
  • Network access is visible and can be disabled.
  • A local backup exists before a migration touches the data.

What we will
not build.

The boundaries are part of the design.

  • A dashboard that exists only to look busy.
  • An agent that hides its tool calls from the person using it.
  • A cloud dependency for a task that can run locally.
  • A release that needs a tutorial before the first useful action.
  • A feature that makes the recovery path harder to explain.
