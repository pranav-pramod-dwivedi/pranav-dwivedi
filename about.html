A working
biography.

The short version, written for someone who has ten minutes.

I build software for the moments after the demo. The useful test is whether a system still makes sense on a bad connection, an old phone, or a day when the person using it is tired. That is where most of my attention goes.

The other half of the work is cricket. I captain Destroyers CC and bat in the middle order. The field teaches a different kind of feedback: the ball does not care how elegant the plan was. You read the situation, choose, and live with the result.

This site is the public index for both. The software lives under Stargaze. The record lives in the scorebook. The rest is context, notes and the occasional argument with a compiler.

Two disciplines,
one test.

The habits transfer even when the tools do not.

01 / PrepareRead the system

Before the first ball or the first commit, find the constraint that will decide the outcome.

02 / DecideChoose the percentage

The best option is rarely the most impressive one. It is the one that leaves room for the next step.

03 / ExecuteMake it real

A plan is only useful when it survives contact with a device, a pitch or a person who has never seen the demo.

04 / AbsorbStay composed

Pressure is information. It tells you where the system is thin and where the next adjustment belongs.

05 / Hand overLeave it clean

The next person should be able to pick up the work without a meeting. That applies to code and to an innings.

06 / RepeatGo again

One good over is not a season. One clean build is not a product. The loop is the work.

What I
optimise for.

The qualities I check before calling something finished.

  • It works without a live demo and a stable connection.
  • A new person can find the entry point in under a minute.
  • The error path is as considered as the happy path.
  • The interface says what it is doing instead of hiding behind a spinner.
  • The build can be replaced in pieces, not all at once.
  • The record can be checked without asking me to explain it.

Software
principles.

Four rules that survive most stack changes.

01Local firstThe useful version runs on hardware you control. The cloud is an option, not the foundation.
02One job per toolSmall services are easier to explain, replace and debug when the system is under pressure.
03Visible stateThe interface should show what the system knows, what it is doing and what it will do next.
04Boring foundationsFiles, processes and sockets before a new platform. The least surprising layer lasts longest.
