Where I am
not the right fit.

A short list saves everyone time.

  • A large team project that needs a full-time engineering manager.
  • A build that depends on a platform I cannot test on a real device.
  • A request for a polished demo before the problem is understood.
  • Work that needs a guaranteed turnaround without a conversation.

Cricket
enquiries.

Club matters have their own route.

For fixtures, selection, club records and the ABV Memorial, the Destroyers CC and RDCA pages are the right source. The club dossier carries the verified record and the public match trail.

If the question is about the software around the record, email is fine. If it is about a match, use the club route. That keeps the scorebook and the build from becoming the same inbox.

Stargaze early
access.

The first release is still in private build.

If you want to test Release 01 on a real device, say what you would use it for and which device you have. The most useful early users are the ones who will hit the permissions, the sync and the recovery paths.

Put “Stargaze” in the subject. A short note about the device and the job to be done is more useful than a feature request list.

Press and
speaking.

A short route for a specific request.

For an interview, a talk or a profile, include the publication, the angle and the deadline. The work is easier to discuss when the questions are specific.

The public record and the work ledger are the best starting points. If the request needs a photograph or a biography, say which format you need and when.

Collaboration.

The best collaborations start with a shared constraint.

I am interested in work where the device, the data or the environment makes the problem specific. Agents, Android, local-first tools, sports vision and editorial interfaces are the closest fit.

A collaboration works when both sides can name what success looks like before the build starts. If the brief is still a moodboard, the first conversation should be about the constraint.

Email
etiquette.

Small conventions that make a thread easier to keep.

  • A subject line that names the project or the request.
  • One clear ask in the first message.
  • Links rather than large attachments where possible.
  • A reply that says what changed, not only that it was received.
  • No urgency language unless the deadline is real.

Privacy
note.

What happens to the message.

Email is used to reply and continue the conversation. It is not added to a mailing list and it is not sold or shared for marketing. The site itself does not run analytics or advertising pixels.

If you want a thread removed after the conversation ends, say so in a reply. There is no account or profile to delete. The privacy page has the longer version.

FAQ:
scope.

The questions that decide whether a note is worth sending.

Can you build X?Probably, if X has a real constraint and a user. Send the short version and the hard part.
Do you take small work?Sometimes. A focused review, prototype or device tool can be a good fit.
Can we start immediately?Only if the scope is small enough to hold. The first step is still a conversation.

FAQ:
timelines.

A realistic view of time.

How fast?A reply usually takes a few days. Build timelines depend on the constraint, not the enthusiasm.
Do you work async?Yes. A written thread is the default, with calls when they add something.
What delays a start?An unclear decision-maker, a moving scope or a platform that cannot be tested.
